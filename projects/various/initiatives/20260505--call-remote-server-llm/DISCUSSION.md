# Discussion: Call Remote Server LLM

## 核心的思想 (Core Philosophy)
> **「サーバー上のエージェントをスマホやMacの『すぐそこ』に引き寄せるためのブリッジ」**

本プロジェクトの目的は、強力なAIエージェント（Claude Code等）を、ネットワークの壁を越えて、あたかも手元のデバイス内で動いているかのように透過的に操作・管理することである。

## Context
個人の作業サーバー上で動くAIエージェントを、スマホやMacから透過的に操作するためのリレーシステムを構築する。当初はロングポーリングによる即時性を検討したが、実装の複雑さを避け、シンプルかつ堅牢な「定期ポーリング＋優先制御」モデルへと舵を切る。

### 3. 抽象的設計 (Abstract Design)

#### A. 入力・中継フェーズ (Portal to Hub)
- **ブリッジ・ポータル (Bridge Portal)**:
    - **役割**: ユーザーが実際に「触る」インターフェース。Slack、Discord、独自Web、あるいはCLIなどの形態をとるが、抽象的には「指示の入力」と「ログの閲覧」を行う窓口。
    - **送信先**: **リレー・ハブ (Relay Hub)**。
    - **リクエスト**:
        - `target_id`: 指示を送る論理サーバーの名前。
        - `thread_id`: やり取りを一括りにするID。
        - `content`: 自然言語による命令、または制御コマンド（中断・承認）。
- **リレー・ハブ (Relay Hub)**:
    - **役割**: ネットワークの壁の外側（インターネット上）に存在する「共有の掲示板・キュー」。ポータルから書き込まれた指示を保持し、サーバーからの要求に応じて払い出す。

#### B. 取得・実行フェーズ (Hub to Remote Server)
- **サーバー・エージェント・マネージャー (Server Agent Manager - SAM)**:
    - **役割**: 各リモートサーバー上で「見回り」を行うコンポーネント。
    - **取得方法**: 定期的にリレー・ハブに対して「自分（論理サーバー名）宛ての新着指示はないか？」を問い合わせ（Fetch）する。
    - **エージェントへの橋渡し**:
        - 取得した内容を **エージェント・アダプター** に渡す。
        - エージェント（Claude Code等）を起動、あるいは稼働中のセッションに指示を投入する。
        - エージェントが吐き出す「思考ログ」や「標準出力」をキャプチャし、**リレー・ハブ** の該当スレッドに書き戻す（Update）。

### 4. 追加要件：複数サーバーの管理
- **論理サーバー名 (Logical Server Name)**:
    - ユーザーは **ブリッジ・ポータル** 上で、操作したいサーバーを論理名で選択する。
    - 各サーバーの **SAM** は、自分の論理名に紐付いた指示のみをフィルタリングして取得する。
    - これにより、1つの **リレー・ハブ** を通じて、複数の「すぐそこ」にあるサーバーを一元管理できる。

## Decisions & Trade-offs (意思決定とトレードオフ)

### 1. リアルタイム性（即時停止）の放棄
- **決定**: ロングポーリングによるミリ秒単位の中断検知を諦め、定期ポーリング（10-30秒）による検知を採用。
- **理由**: 中継サーバー（Node.js/Nginx）の独自実装・維持コストが、今回の「個人開発」というコンテキストに対して過大であると判断。
- **代償**: ユーザーが「停止」を押してから実際にサーバーが止まるまでに最大30秒程度のタイムラグが発生する。

### 2. 独自リレーサーバーの不採用
- **決定**: 中継地点としてGitHub API、Slack、または既存のKVS SaaSを活用する。
- **理由**: セキュリティ（認証・暗号化）や可用性の実装を既存基盤に委ねることで、開発リソースを「エージェントの操作体験」に集中させるため。
- **代償**: 外部サービスのレートリミットやダウンタイムの影響を受ける可能性がある。

### 3. ポーリング負荷の許容
- **決定**: 低頻度（10-30秒）のポーリングを常時走らせる。
- **理由**: ネットワークの壁を越えるための最も確実でシンプルな方法であるため。
- **代償**: サーバー側で常に微小なネットワークトラフィックとログが発生し続ける。

## 結論 (Conclusion)
...
本システムは、**「サーバー上のエージェントをスマホやMacの『すぐそこ』に引き寄せるためのブリッジ」** として、高度なリアルタイム性よりも **「シンプルで壊れにくく、かつ確実に止められる」** 信頼性を最優先し、定期ポーリングとサーバー側優先制御によって目的を達成する。
