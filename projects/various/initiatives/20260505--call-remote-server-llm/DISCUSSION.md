# Discussion: Call Remote Server LLM

## 核心的思想 (Core Philosophy)
> **「サーバー上のエージェントをスマホやMacの『すぐそこ』に引き寄せるためのブリッジ」**

本プロジェクトの目的は、強力なAIエージェント（Claude Code等）を、ネットワークの壁を越えて、あたかも手元のデバイス内で動いているかのように透過的に操作・管理することである。

## Context
個人の作業サーバー上で動くAIエージェントを、スマホやMacから透過的に操作するためのリレーシステムを構築する。当初はロングポーリングによる即時性を検討したが、実装の複雑さを避け、シンプルかつ堅牢な「定期ポーリング＋優先制御」モデルへと舵を切る。

### 2. 抽象的設計 (Abstract Design)

#### A. 入力・中継フェーズ (Portal to Hub)
- **ブリッジ・ポータル (Bridge Portal)**: 
    - ユーザーが操作する窓口（Slack, Web等）。
    - リレー・ハブへ `target_id`, `thread_id`, `content` を送信する。
- **リレー・ハブ (Relay Hub)**: 
    - インターネット上の共有掲示板。指示を保持し、サーバーからの要求に応じて払い出す。

#### B. 取得・実行フェーズ (Hub to Remote Server)
- **サーバー・エージェント・マネージャー (Server Agent Manager - SAM)**: 
    - 各サーバー上の見回り役。自分宛ての指示をハブから取得（Fetch）する。
- **エージェント・アダプター (Agent Adapter)**: 
    - SAMとLLMエージェント（Claude Code等）を繋ぐ通訳。
    - 擬似ターミナル(PTY)を用いてエージェントの入出力を透過的にキャプチャし、ハブに書き戻す。

### 3. 追加要件：複数サーバーの管理と識別
- **サーバーの固有性 (Server Identity)**: 
    - 各サーバー（例：GPU搭載機、ストレージサーバー等）は、それぞれ固有の役割を持つ。
    - ユーザーは「何をやらせたいか」に応じて、操作対象のサーバーを明確に選択する。
- **論理サーバー名 (Logical Server Name)**: 
    - そのサーバーの「役割」や「個性」を表す名前（例：`gpu-machine`, `home-nas`）。各サーバーのローカル設定（`.env`等）で定義する。
- **共有サーバー名簿と選択 (Registry & Selection)**: 
    - **唯一の参照先**: Relay Hub 内に、全サーバー・ポータルが共通して参照する「名簿（名前空間）」を設ける。
    - **サーバー側 (SAM)**: 自分自身の論理名に対応するレコード（例：`/servers/A/status`）を、生存報告（Heartbeat）として定期的に更新する。
    - **ユーザー側 (Portal)**: 同じ「名簿」を参照することで、現在オンラインなサーバー（個性）を動的に発見し、ユーザーに提示する。

### 4. 詳細設計：ツール・ライブラリ選定 (Detailed Tool Selection)

#### A. リレー・ハブ (Relay Hub) の候補
1. **GitHub Issues / Discussions (API)**: 強力な認証とスレッド構造。レートリミットが懸念。
2. **Upstash Redis (Serverless Redis)**: 低レイテンシ。スレッド管理の自前実装が必要。
3. **Slack / Discord (Webhooks & API)**: 通知とスマホ入力に最適。ログの長大化に課題。

#### B. ブリッジ・ポータル (Bridge Portal)
1. **Slack (App / Bolt)**: 既存チャットUIを活用。
2. **Custom Web App (Vercel + Next.js)**: 独自UIによる高度な制御。

#### C. サーバー・エージェント・マネージャー (SAM)
1. **Node.js (TypeScript)**: Claude Code等のエージェント（JS/TS）との親和性。
2. **Python**: `subprocess` や `threading` による堅牢な制御。

#### D. エージェント・アダプター
1. **node-pty (Node.js)** / **ptyprocess (Python)**: ターミナル対話の完全な透過性を確保。

## Decisions & Trade-offs (意思決定とトレードオフ)

### 1. リアルタイム性（即時停止）の放棄
- **決定**: ロングポーリングではなく定期ポーリングを採用。
- **代償**: 中断検知までに最大30秒程度のラグ。

### 2. 独自リレーサーバーの不採用
- **決定**: GitHub API, Slack 等の既存インフラを活用。
- **代償**: 外部サービスの制限やダウンタイムの影響。

### 3. ポーリング負荷の許容
- **決定**: 10-30秒間隔の常時ポーリング。
- **代償**: 微小な継続トラフィック。

## 結論 (Conclusion)
本システムは、**「サーバー上のエージェントをスマホやMacの『すぐそこ』に引き寄せるためのブリッジ」** として、シンプルさと堅牢性を最優先し、定期ポーリングとサーバー側優先制御によって、リモートでの自律的な作業環境を提供する。
