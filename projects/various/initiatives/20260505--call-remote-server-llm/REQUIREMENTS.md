# Requirements Specification: Call Remote Server LLM Bridge

## 1. はじめに (Introduction)

### 1.1 目的
個人の作業サーバー上で稼働する強力なAIエージェントを、ネットワーク隔離された環境下において、スマホやMacから透過的に操作・管理するためのリレーシステム（ブリッジ）の要件を定義する。

### 1.2 核心的思想 (Core Philosophy)
> **「サーバー上のエージェントをスマホやMacの『すぐそこ』に引き寄せるためのブリッジ」**
本システムは単なる通信手段ではなく、リモートの自律エージェントをあたかも手元のデバイス内で動かしているかのような操作感と、絶対的な制御権をユーザーに提供することを目指す。

## 2. 機能要件 (Functional Requirements)

### 2.1 透過的ステート同期
- **FR-1: 実行ログの転送**: サーバー上のエージェントの標準出力、標準エラー、および思考プロセス（Thought）を定期的に中継地点へ同期し、ローカルから参照可能にすること。
- **FR-2: インタラクティブ対話のリレー**: エージェントがユーザーの入力を待機している状態を検知し、ローカルデバイスからの回答をサーバーへ転送すること。
- **FR-3: スレッド管理**: 1つの用件を「スレッド（またはIssue）」として管理し、文脈を維持した継続的な指示を可能にすること。

### 2.2 制御と安全性
- **FR-4: 優先的中断制御**: 定期ポーリングにおいて「中断（STOP）」指示を最優先で確認し、検知した場合は現在の作業を即座に破棄・プロセス停止させること。
- **FR-5: 承認ワークフロー**: 破壊的な操作や高コストなAPI利用の前に、ユーザーの明示的な承認を待機する仕組みを提供すること。

### 2.3 セッション管理
- **FR-6: 非同期マルチセッション**: 複数の独立した作業スレッドを並行して管理し、個別に進捗を追跡できること。
- **FR-7: 永続性と再開**: 通信断が発生してもサーバー側の実行は継続し、再接続時に最新の状態から操作を再開できること。

## 3. 品質特性 (Quality Attributes)

### 3.1 信頼性・堅牢性
- **QA-1: IDベースの冪等性**: 全ての指示に一意のIDを付与し、ネットワーク不安定による再送時の二重実行を確実に防止すること。
- **QA-2: シンプルな構造**: 特殊なプロトコルや独自サーバーを避け、標準的なHTTPポーリングによる、壊れにくく保守しやすい構造であること。

### 3.2 セキュリティ
- **QA-3: 通信の秘匿性**: 指示内容およびログに機密情報が含まれることを前提とし、エンドツーエンドまたは中継地点での適切な暗号化を行うこと。
- **QA-4: 厳格な認証・認可**: 信頼された特定のデバイスのみが指示を送信・閲覧でき、第三者によるコマンド注入を完全に排除すること。

### 3.3 安全性
- **QA-5: 制御の確実性**: サーバー側の監視スクリプトがエージェントに対して絶対的な強制停止権限（SIGKILL等）を持つこと。

## 4. 制約条件とトレードオフ (Constraints & Trade-offs)

### 4.1 通信方式
- インターネットを介した定期ポーリング（10-30秒間隔）を基本とする。

### 4.2 トレードオフの承認
- **リアルタイム性の制限**: 即時停止（ミリ秒単位）ではなく、次回のポーリングタイミングでの停止を許容する。
- **外部依存の受容**: 独自リレーサーバーを構築せず、GitHub API等の既存SaaS基盤を活用することによる外部依存リスクを許容する。

## 5. 将来の拡張性 (Future Scope)
- 生成物のプレビュー機能（HTML/画像等のローカル表示）。
- 音声入力による指示。
- モバイルアプリ（プッシュ通知連携）による承認フローの最適化。
