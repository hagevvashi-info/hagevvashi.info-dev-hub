# Architecture Design: Call Remote Server LLM Bridge

## 1. アーキテクチャの意思 (Architectural Intent)

本システムのアーキテクチャは、**「不確実なネットワーク環境下での、シンプルかつ絶対的な制御の確立」** を最優先事項として設計されている。

高度なリアルタイム性（ミリ秒単位の応答）を追求してシステムを複雑化させるのではなく、あえて **「定期ポーリングによる非同期通信」** を基盤とすることで、ネットワーク隔離、通信断、およびサーバーの自律実行に対する堅牢性を確保する。ユーザーに提供するのは「即時性」そのものではなく、**「自分の指示が確実に届き、いつでも確実に止められる」という信頼感** である。

## 2. アーキテクチャ・スタイルとパターン

### 2.1 ハブ・アンド・スポーク型非同期リレー (Hub-and-Spoke Async Relay)
インターネット上に配置された **Relay Hub** を中心に、ユーザー側の **Bridge Portal** とサーバー側の **SAM (Server Agent Manager)** がそれぞれ独立して通信を行うスタイル。
- **メリット**: 両者が直接繋がっている必要がなく、ネットワーク隔離（Firewall/NAT）を透過的に回避できる。
- **状態の局所化**: 全ての「指示」と「進捗」のマスターデータは Hub に集約され、Portal と SAM はそのスナップショットを同期する。

### 2.3 セントラル・レポジトリによる統治 (Central Repository Governance)
サーバーの定義（名前、役割、認証ID）を **マスター・コンフィグ** として一元管理し、これを Relay Hub 上に配置する。Bridge Portal と Remote Server の双方がこのマスターを「引き抜く（Pull）」ことで、システム全体の整合性を保つ。
- **意図**: ユーザーによる直接的な統治。サーバーの自己申告を許さず、ユーザーが定義した「真実のソース」を全てのコンポーネントが参照する。

## 3. 主要コンポーネントとその責務

### 3.1 Bridge Portal (ポータル)
- **責務**: ユーザーインターフェースの提供。
- **設計の意思**: 操作性を重視し、複雑なロジックは持たせない。指示を Hub に投げ、Hub から返ってくるログを表示することに専念する。

### 3.2 Relay Hub (ハブ)
- **責務**: 指示の永続化、キューイング、および状態の仲介。
- **設計の意思**: 自前でのホスティングを避け、GitHub API、Slack、またはKVS SaaS等の **「既存の信頼できるインフラ」** を活用する。これにより、可用性とセキュリティ（認証/SSL）の責任を委譲する。

### 3.3 Server Agent Manager (SAM)
- **責務**: ポーリング、指示の解釈、エージェントのプロセス管理。
- **設計の意思**: **「絶対的な統治者」**。エージェント（Claude Code等）を子プロセスとして制御し、Hub から「中断」指示を読み取った際は、エージェントの状態に関わらず即座に強制停止させる。

## 4. 重要な設計判断とトレードオフ (Design Decisions & Trade-offs)

### 4.1 リアルタイム性 vs 堅牢性 (Simplicity Over Latency)
- **判断**: ロングポーリングやWebSocketを排し、10-30秒間隔の定期ポーリングを採用。
- **理由**: 常時接続の維持に必要な再接続ロジックやサーバー負荷の管理コストを削減し、スクリプトレベルで実装可能な「壊れにくさ」を優先。
- **影響**: 中断ボタンを押してから実際に止まるまでにタイムラグが生じるが、これを「仕様（安全のための確認時間）」として許容する。

### 4.2 論理名によるルーティング (Logical Addressing)
- **判断**: 物理的なIPやホスト名ではなく、ユーザーが定義した「論理サーバー名」で指示を配送する。
- **理由**: サーバーが複数ある環境や、クラウド/ローカルが混在する環境でも、ユーザーが一貫したインターフェースで操作できるようにするため。

### 4.3 IDベースの冪等性確保
- **判断**: 全てのコマンドにUUIDを付与し、SAM側で「実行済み履歴」を保持する。
- **理由**: ネットワーク不安定によるリトライ時に、同じ「Slackに返信」という指示が二度実行されるなどの副作用を防止するため。

## 5. セキュリティ・アーキテクチャ

- **通信保護**: 既存のSaaS（HTTPS）を利用することで、輸送中の暗号化を担保する。
- **認証**: リレー・ハブへのアクセスには、ポータル・サーバー共に共通のアクセストークン（秘密鍵）を必要とする。
- **最小権限**: SAMは、Hub からの読み取りと、自身のステータス書き込みのみを許可される権限で動作することを推奨する。

## 6. 結論 (Summary)

本アーキテクチャは、**「サーバー上のエージェントをスマホやMacの『すぐそこ』に引き寄せる」** というビジョンを、最も低コストかつ高信頼な方法で実現するためのものである。複雑さを削ぎ落とし、既存のWebインフラをブリッジとして活用することで、開発リソースをエージェントの高度な活用へと振り向けることを可能にする。
